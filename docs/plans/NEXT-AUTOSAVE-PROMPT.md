## Задача и границы

Сделай автосохранение в IndexedDB: после обновления страницы или закрытия и повторного открытия браузера можно восстановить тексты, настройки, порядок проектов/снимков, обложки и НОВЫЕ изображения.

Работает в статической админке GitHub Pages и локальном режиме. Автосохранение не отправляет ничего на GitHub и не публикует сайт. Не начинай обрезку, drag-сортировку, OAuth, переделку дизайна или других разделов.

Используй существующие data, uploads, history, documentEpoch и мост предпросмотра. Добавь небольшой отдельный модуль хранения и интеграцию в admin.js; второй модели документа и второй истории не нужно.

## Что хранить

- Версию формата, идентичность рабочего пространства, время, ревизию записи.
- Снимок текущего документа и его исходную базу для сравнения, базовый GitHub head.
- Blob новых изображений, на которые ссылается этот снимок. JSON и соответствующие Blob должны фиксироваться согласованно в одной транзакции.
- Разделяй записи по owner/repo/branch и режиму local/GitHub. Разные origin браузер уже разделяет сам.

Не сохраняй токены, заголовки авторизации, объект GitHub-клиента или blob: URL. URL временные: после восстановления создавай новые через URL.createObjectURL. Восстанови структуру uploads, включая bytes, необходимые существующему github.save. Один файл, используемый несколько раз, хранится один раз.

Историю Undo между запусками в этом этапе сохранять НЕ требуется. После восстановления она начинается заново; обычные Undo/Redo в текущем сеансе должны продолжать работать. Не удаляй из памяти файлы, которые ещё нужны текущей истории.

## Когда сохранять и как показывать состояние

Подключи автосохранение к единой точке изменения документа, включая старую форму, живой инспектор, Undo/Redo, импорт и завершение обработки изображений. Для текста достаточно задержки около 600 мс; атомарные действия можно сохранять сразу.

Снимок захватывай целиком, не передавай в асинхронную запись изменяемую ссылку data. Старое завершение записи не должно объявлять более новую правку сохранённой. Сериализуй записи; промежуточные ожидающие снимки можно объединять до последнего. Не держи IndexedDB-транзакцию открытой во время сжатия картинки или внешнего await.

Рядом с существующим статусом GitHub показывай отдельный краткий статус:
- «Сохраняю на этом устройстве…»
- «Черновик сохранён на этом устройстве»
- «Не удалось сохранить черновик» с доступной причиной/повтором.

Успех показывай только после завершения транзакции для актуальной ревизии. Не сбрасывай dirty: локальное сохранение не означает сохранение на GitHub. Экспорт «Скачать JSON» тоже не является публикацией и не должен удалять локальный черновик.

Не обещай, что произвольное закрытие вкладки до завершения записи всегда сохранит последнюю букву. Начинай сохранение заранее; visibilitychange/pagehide могут ускорить ожидающую запись, но не являются гарантией. Пока есть несохранённые локально изменения, обработка картинок или ошибка хранилища, сохраняй предупреждение об уходе. Не полагайся на await в beforeunload.

## Восстановление и смена документа

В GitHub-режиме проверяй доступ владельца существующим способом; локальный черновик не заменяет авторизацию. После загрузки соответствующего репозитория предложи восстановить найденную копию с временем сохранения. При совпадающей базе восстановление должно быть простым.

Если удалённый head изменился с момента создания черновика, не подменяй молча актуальные данные и не отправляй старый документ поверх них. Сохрани локальную копию, покажи расхождение и предложи осознанно открыть её либо продолжить с актуальными данными. Автоматическое сложное слияние сейчас не нужно.

Проверяй структуру записи и наличие нужных Blob. Полную validateContent для публикации не используй как единственный фильтр черновика: человек может закрыть вкладку с пустым названием или незаполненной подписью. Такие допустимые незавершённые правки нужно восстановить. Строгую проверку перед GitHub-сохранением оставь.

После восстановления: согласованно заменить data и uploads, увеличить documentEpoch, сохранить устойчивые project/shot id, инициализировать историю, обновить старую форму и iframe. Не считай новый случайно созданный id при загрузке старого JSON конфликтом содержимого: сохрани исходный снимок/базу и используй согласованное сравнение dirty.

Перечитать, импорт, выход и успешное сохранение на GitHub должны явно взаимодействовать с очередью IndexedDB. Запоздалая запись прежнего документа не должна воскресить отменённый черновик. При успешном GitHub-сохранении обнови локальную базу либо очисти соответствующий черновик только после успешного завершения операции. При ошибке GitHub черновик остаётся. Выход удаляет токен из памяти, но не должен автоматически уничтожать сохранённую локальную работу.

## Несколько вкладок и ошибки

Две вкладки одного рабочего пространства не должны молча перезаписывать изменения друг друга. Проверяй ожидаемую ревизию записи внутри той же IndexedDB-транзакции. При конфликте останови автозапись этой вкладки, сохрани её текущие данные в памяти и покажи понятный выбор перечитать/экспортировать. Одного BroadcastChannel без проверки записи недостаточно.

Отказ IndexedDB, переполнение квоты или повреждённая запись не должны ронять редактор или показывать ложный успех. Оставь ручное редактирование и существующий экспорт доступными. Не удаляй базу целиком в ответ на любую ошибку.

## Проверка и завершение

Нужны проверки конкретных сценариев, без большого количества тестов, повторяющих код:

1. Текст + новая картинка + перестановка → дождаться статуса → reload → восстановить → данные и реально отображаемое изображение на месте, включая iframe.
2. Незаполненное поле черновика восстанавливается, а строгая проверка публикации по-прежнему его отклоняет.
3. Быстрые правки, Undo/Redo и медленная запись: после завершения восстановится последняя версия.
4. Перечитать/импорт/выход при ожидающей записи: старый снимок не возвращается.
5. Новый файл используется в нескольких местах; восстановлены один Blob и все ссылки.
6. Ошибка квоты/транзакции: нет ложного статуса успеха, предыдущая целая копия сохранна.
7. Две вкладки: нет молчаливой потери правок.
8. Разные ветки/репозитории/режимы не смешиваются; изменившаяся удалённая база распознаётся.
9. Успешное/неуспешное GitHub-сохранение согласуется с локальной копией. На этом этапе проверь это через тестовый адаптер: реальную запись на GitHub/main ради теста не делай.
10. Восстановление не теряет поддержку старого JSON, обычное редактирование и Undo/Redo.

В модульных тестах проверяй реальный модуль хранения через подходящий IndexedDB-адаптер; не подменяй сам проверяемый алгоритм собственной реализацией. В браузере обязательно проверь реальную IndexedDB и настоящий reload с новым изображением.

Прогони штатные тесты, build/TypeScript, lint и check:content. В отчёте раздели реальные браузерные проверки, тесты с адаптером и ограничения. Существующие шесть предупреждений линтера назови отдельно от новых ошибок.

Сделай связный коммит, отправь в рабочую ветку без force и пришли SHA. main и публикацию не трогай. После выполнения этого задания остановись: следующий и заключительный этап — проверка реального входа/сохранения/обновления GitHub Pages.
