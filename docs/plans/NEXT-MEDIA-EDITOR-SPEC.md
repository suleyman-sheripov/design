# Следующий этап: визуальный редактор изображений — техническое задание

Продолжай текущую ветку claude-live-editor-bridge репозитория suleyman-sheripov/design. Последняя проверенная точка — b93dc9a. Если ты уже начал следующий этап, сохрани работу и применяй это уточнение поверх неё. Не откатывай новые коммиты, не используй force, не меняй main и не публикуй сайт.

Задача — удобное управление изображениями выбранного проекта в инспекторе. Не новый конструктор сайта. Публичный дизайн, интро, логотип, лента и переходы сохраняются. Основа состояния, history.js, защита асинхронных операций и bridge уже есть; используй их. Не создавай второй draft или независимую историю в медиадиалоге.

## 1. Точный пользовательский результат

В инспекторе проекта три ясно отделённых блока:

1. «Превью в подборке»: большая миниатюра, заменить, выбрать из медиа, отображение.
2. «Обложка кейса»: отдельная миниатюра и те же действия; явное состояние «Использовать превью».
3. «Галерея»: сетка снимков, добавить, заменить конкретный, изменить подпись, переместить, удалить из галереи.

Общий медиадиалог имеет миниатюры, поиск, загрузку, размеры и выбор. Он открывается для конкретной цели: пользователь видит, что именно меняет. «Отмена» закрывает диалог без изменения документа. Файловый input доступен помимо drop-зоны. У всех интерактивных элементов понятные подписи и фокус.

На 390 px диалог и инспектор остаются удобными для пальца, без горизонтального скролла всей страницы. Не мельчи три колонки. Переключение между инспектором и preview сохраняет выбранный проект и положение страницы.

## 2. Семантика данных — не угадывать

- cover — отдельная ссылка на файл для карточки подборки.
- caseCover — отдельная ссылка на обложку кейса. Если пусто, действует существующий fallback на cover. В интерфейсе это явно называется «Использовать превью».
- shots — упорядоченные вхождения снимков в галерею со своими подписями.
- Изменение cover НЕ меняет явно заданную caseCover и shots. Если включено «Использовать превью», обложка кейса закономерно меняется вместе с cover: это не ошибка независимости.
- Замена снимка галереи меняет только выбранное вхождение. Два вхождения одного файла остаются двумя элементами.
- Удаление из галереи не удаляет физический файл, не сбрасывает обложки и не меняет другие проекты. Кнопки физической очистки репозитория здесь не нужны.
- Повторный выбор существующего файла использует прежнее имя/reference; новый бинарный файл не создаётся. Дедупликация одинаковых заново загруженных байтов по хешу сейчас не обязательна.

Идентификатор файла, идентификатор проекта и идентификатор вхождения в галерею — разные сущности. Не используй индекс массива как долговременную цель асинхронной операции. Для галереи введи устойчивую идентичность вхождения, совместимую с Undo/Redo. Допустимо добавить optional id к снимкам и валидировать его уникальность внутри проекта. Для старого JSON продумай однократную нормализацию, не генерируй id на каждом render. Опиши миграцию и её отражение в saved/dirty; не создавай ложное сообщение о публикации.

## 3. Минимальная архитектура

Раздели UI медиадиалога, получение списка медиа, команды изменения документа и передачу assets в preview. Не делай глобальные переменные selectedProject/selectedIndex единственным способом понять цель.

Ориентир команды (адаптируй к текущим типам):

```text
Target = projectId + slot(cover | caseCover | gallery) + optional galleryItemId
selectExistingAsset(Target, assetId)
uploadForTarget(Target, File)
removeGalleryItem(projectId, galleryItemId)
moveGalleryItem(projectId, galleryItemId, relativePosition)
updateImagePresentation(Target, fit, position)
```

Команда проверяет существование текущей цели и разрешённость значения, завершает предшествующую текстовую транзакцию, затем создаёт одно смысловое действие истории. UI обновляется через существующие уведомления. Не меняй DOM как способ сохранить данные.

Медиатека вычисляется из доступных файлов репозитория плюс локальных uploads. Данные об использовании получай из текущего draft, а не отдельного изменяемого счётчика. Если размер существующего изображения неизвестен, покажи это честно и получай его по мере загрузки; не декодируй все изображения заранее ради открытия диалога. Миниатюры грузятся по необходимости, без сканирования GitHub при каждой букве поиска.

В JSX разрешаются имена файлов из модели, а не произвольные URL из текстового поля. Сохрани ограничения форматов, размеров и безопасных путей. Ошибка одного изображения в медиатеке не обрушает весь список.

## 4. Асинхронные операции: обязательные правила

Переиспользуй существующие documentEpoch, счётчик обработки и per-target operation id. Защита должна применяться ко всем новым путям загрузки, включая замену одного элемента галереи и старую форму, если она остаётся доступной.

После каждого await до изменения draft/uploads/history заново проверь epoch, актуальность операции и существование цели. Для replace побеждает последний выбор пользователя, а не последнее завершение декодирования. Сортировка галереи во время загрузки не меняет адресата замены.

Для добавления нескольких файлов заранее зафиксируй их порядок. Параллельное сжатие не должно переставлять снимки по скорости выполнения. Для первой версии допустима последовательная обработка небольшой пачки. Выбери и явно реализуй одну политику ошибок: рекомендуемый вариант — подготовить всю пачку и добавить её одним действием только при успехе всех файлов; при ошибке показать файл и причину, подготовленные временные ресурсы освободить. Не добавляй молча половину пачки.

Закрытие медиадиалога до подтверждения аннулирует выбор/операцию этой сессии. Undo, import, Reload, выход и удаление цели аннулируют соответствующие незавершённые операции. Поздний результат не создаёт «призрачную» правку. Для этого жизненный цикл диалога/операции может требовать отдельного поколения, помимо documentEpoch.

При обработке файлов публикация блокируется с понятным статусом. inert не отменяет Promise. Ошибка или отмена всегда снимают занятость. Устаревший результат освобождает свои временные URL, но не ресурсы другого активного задания.

Не вставляй подготовленный файл в uploads до проверки актуальности. После применения файла его ресурс не освобождается, пока он нужен draft, истории или preview. Используй уже исправленный протокол передачи и подтверждения assets, не возвращай пересылку Blob на каждый символ текста.

## 5. Отображение и фокус картинки

«Вписать» показывает изображение целиком без искажения. «Заполнить» заполняет рамку с обрезкой. Точка фокуса выбирается в миниатюре; значения нормализованы и ограничены допустимым диапазоном. Есть «По центру» и доступный способ изменения без перетаскивания.

Сначала проверь текущую модель: previewFit/previewPosition сейчас могут совместно влиять на cover и caseCover. Не обещай независимое оформление двух областей, если меняешь одно общее поле. Если делаешь независимые настройки — добавь обратно совместимые поля с явным fallback, обнови TypeScript, общую валидацию, публичный ProjectArt, preview, импорт/экспорт и тесты вместе. Альтернатива — честно обозначить общую настройку до отдельного этапа. Выбранный вариант зафиксируй в коротком плане перед изменениями, без остановки на необязательное согласование.

Обрезка недеструктивна: исходный файл не переписывается. Не меняй глобальную запись asset при изменении кадрирования одного его использования.

Перетаскивание фокуса: начало транзакции → живые обновления → один commit на завершение. Escape/pointercancel возвращает исходное значение и не добавляет историю. Обрабатывай отпускание указателя за пределами миниатюры; числовой fallback не должен позволять NaN/Infinity. Преобразование координат учитывает реальные размеры и область отображения миниатюры; не смешивай экранные пиксели с процентами.

## 6. Сортировка и история

Перестановка за ручку, а не за всю кликабельную картинку. Доступны кнопки перемещения и клавиатура; на touch страница должна нормально прокручиваться вне ручки. Один завершённый reorder — одно действие Undo. Отменённое перетаскивание — ноль действий. Фокус после перестановки остаётся на том же снимке по устойчивому id.

Замена cover, смена caseCover, добавление пачки, замена конкретного снимка и удаление — отдельные атомарные действия. Undo/Redo возвращает одновременно документ, инспектор и preview, включая картинку. Не смешивай завершившуюся загрузку с текстом, который пользователь в этот момент печатает: предварительно зафиксируй открытую текстовую транзакцию через общий механизм, сохранив её отдельным шагом.

Не изменяй историю внутри render. Не сбрасывай Redo при простом открытии/закрытии диалога или выборе той же самой картинки. Настоящая новая правка после Undo должна очистить прежнюю ветку Redo.

## 7. Проверка по сценариям, а не по количеству тестов

Обязательны автоматические проверки команд/гонок/истории и браузерные проверки взаимодействия:

1. Изменить cover при явно заданной другой caseCover: галерея и caseCover неизменны. Повторить с «Использовать превью»: fallback работает ожидаемо.
2. Выбрать существующий файл: uploads не растёт. Тот же asset использовать в двух местах, удалить одно вхождение: второе работает.
3. Замена A → B с обратным порядком окончания: побеждает B.
4. Начать замену снимка, переставить галерею: обновляется правильный id. Удалить цель/Undo/Reload/закрыть диалог до завершения: позднего изменения нет.
5. Добавить пачку с разным временем обработки: порядок исходный. Один повреждённый файл: соблюдается выбранная политика, нет зависшего статуса и скрытой частичной записи.
6. Двигать фокус, отменить Escape; затем применить и выполнить Undo/Redo. Исходный файл цел, история не посимвольная/покадровая.
7. Reorder мышью, кнопками и на узком экране. Отмена не меняет порядок. Фокус и скролл стабильны.
8. После замены картинки напечатать текст: src неизменённой картинки стабилен. Перезагрузить iframe, выполнить Undo/Redo картинки: изображение остаётся доступно.
9. Два проекта с одинаковыми названиями, два вхождения одного изображения, переименование slug: цель операций не путается.
10. Проверить мобильный редактор на 390 px и широкий экран; показать скриншоты. Ошибки доступны рядом с действием, клавиатурный фокус видим.
11. Старый JSON без новых optional полей загружается. Неверный тип настройки/снимка не доходит до опасного рендера. Пустое редактируемое текстовое поле не блокирует весь preview.
12. Test/build/lint и обычное открытие кейса: обложка не растягивается в переходе. Настоящую запись в main для проверки не выполнять.

Сначала реализуй один законченный вертикальный срез: выбор из медиа → изменение cover → live preview → Undo/Redo. Затем применяй тот же механизм к caseCover/галерее, затем настройкам отображения и reorder. Сохраняй этапы отдельными осмысленными коммитами; не коммить каждую правку комментария отдельно и не повторяй полный аудит после косметических изменений.

## 8. Условие завершения

Покажи работающий редактор, ссылки на коммиты и результаты перечисленных сценариев. Разделяй проверки в браузере, тесты с искусственными задержками и непроверенные предположения. Если новая проверка обнаружила дефект — исправь и повтори затронутый сценарий. Если этап прошёл, остановись с результатом, не запускай бесконечную «проверку ради спокойствия».

IndexedDB, остальные секции и полный редизайн админки сейчас вне этого этапа. Не объявляй весь редактор законченным после работы только с изображениями. При сложной проблеме пришли ведущему конкретный файл, воспроизведение, ошибку и минимальный diff; не заменяй нерешённую механику декоративной кнопкой.
