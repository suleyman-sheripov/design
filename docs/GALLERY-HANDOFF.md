1. Проверь git status, ветку и HEAD.
2. Сохрани свои незакоммиченные правки галереи в отдельную WIP-ветку/коммит. Не удаляй и не накладывай их автоматически: Codex реализовал тот же этап независимо, поскольку твоя галерея не была отправлена на GitHub.

4. Прочитай дифф контрольного коммита относительно 46d6954. Исправления обложек в 46d6954 уже сохранены. Не возвращайся на 9a213e9 или 7715bfd.

## Что уже реализовано

- Галерея в живом инспекторе: миниатюры, подписи, добавление из медиатеки/загрузка одного файла, замена, «Выше», «Ниже», удаление вхождения.
- «Открыть кейс в предпросмотре» открывает страницу проекта внутри iframe, сохраняя инспектор. Это нужно для непосредственной проверки галереи.
- Каждое вхождение shots имеет устойчивый id. Один файл разрешён в нескольких вхождениях. ensureShotIds в model.js вызывается при загрузке/импорте через stampProjectIds до начального снимка истории. Старый JSON без id читается; дубли id отвергаются. Новые снимки старой формы и копии проектов получают новые id.
- Команды gallery-add / gallery, removeGalleryItem / moveGalleryItem используют существующую историю, epoch и идентичность цели. Нет пустой записи до окончания загрузки. Отмена/устаревший результат не оставляет upload. Перестановка не меняет цель незавершённой замены.
- Удаление не удаляет бинарные файлы; обложки cover/caseCover независимы. Перемещение/удаление возвращают фокус на актуальный элемент.
- Подпись можно редактировать отдельно; для нового снимка она пустая, интерфейс предлагает заполнить её перед публикацией. Существующая строгая проверка публикации сохранена.
- CasePage использует key по shot.id с совместимым fallback.
- Исправлен счётчик загрузок при перечитывании: load больше не обнуляет pendingImageJobs, пока старые операции ещё завершаются.
- Добавлены gallery.test.mjs, case-gallery.test.mjs и регрессии в bridge.test.mjs.

## Точное место остановки

При загрузке настоящего WebP новая картинка появилась в инспекторе, но в галерее CasePage обнаружился пропуск интеграции: она читала только shotSrc(file), обходя Blob из живого моста.

Codex УЖЕ исправил это: CasePage получает useEditBridge() и использует bridge.assetUrl(shot.file) ?? shotSrc(shot.file). Добавлены два теста рендеринга настоящего CasePage: приоритет живого Blob и fallback для опубликованных файлов.

После этой правки последние сохранённые результаты: 98/98 тестов и успешная сборка с TypeScript. До финальной правки lint выдавал шесть существующих предупреждений в React-компонентах; check:content проходил. Финальный lint/check:content нужно повторить.

Финальная проверка картинки в браузере НЕ завершена. В DOM iframe после правки появился blob: URL, однако naturalWidth/complete не подтвердили декодирование: снимки lazy-loaded, а попытка прокрутки/клика браузерным инструментом завершилась ошибкой видимости. Нельзя выдавать наличие src за доказательство, что изображение действительно видно. Это первый оставшийся пункт.

## Что доделать — узко и по порядку

1. Запусти текущие тесты, убедись, что старт соответствует контрольному коммиту.
2. В свежей сессии локального черновика выбери проект → «Открыть кейс в предпросмотре» → загрузи НОВЫЙ файл именно в галерею. Доскролль iframe до снимка. Подтверди реальное изображение визуально и ненулевые naturalWidth/naturalHeight после загрузки. Проверь Undo → Redo и повторную загрузку iframe: Blob должен доставиться снова, изображение должно остаться видимым. Если есть баг — исправь причину, не обходи мост глобальными переменными или постоянным сохранением blob: URL.
3. Проверь добавление/замену/перестановку/удаление, два вхождения одного файла, раздельные Undo/Redo. После удаления последнего элемента — пустая галерея, фокус на добавлении. Обложки не меняются.
4. Проверь старую форму: её добавление/замена/перестановка, подписи и повторный импорт не ломают id и синхронизацию инспектора.
5. Экспортируй тестовый JSON, импортируй обратно. Проверь порядок/id/подписи, а также сообщение о необходимости повторно загрузить новые бинарные файлы, если они отсутствуют. JSON сам по себе не содержит бинарные изображения; IndexedDB здесь ещё нет. Не обещай восстановление файлов из одного JSON.
6. Проверь клавиатуру и настоящий viewport 390 px. Сначала измерь фактическую ширину, затем интерфейс/прокрутку/кнопки/фокус. Если инструмент не позволяет — честно отметь ограничение.
7. Финально: npm test, npm run build, npm run lint, npm run check:content, git diff --check. Устрани новые ошибки; старые предупреждения назови отдельно.
8. Закоммить только необходимые исправления поверх контрольного коммита, push без force, пришли SHA и конкретные результаты. Если код уже исправен, достаточно отчёта о проверках — не создавай косметические коммиты ради активности.
